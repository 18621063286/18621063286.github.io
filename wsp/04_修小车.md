# 第 4 章　一次回复，修好一个失败的控制策略

> 原实验：`upstream/exp4_fix_car/`　|　博客：Experiment 4　|　难度 ★★★　|　全部只需 CPU（评测用 JAX + Kinetix 的 CPU 版，1,024 局约 5 分钟）

## 4.1 问题

Kinetix 物理环境里有一关叫"小车上坡"（`l/h2_car_ramp`）：小车要先**倒车**，再全速向左冲，跳过一条红色地带，最后碰到蓝色方块才算成功。
用官方 PPO 训练了 10 亿步的策略网络 `679 → 128 → 5×128 → 16`（171,664 个权重），**256 局全部失败**：它每次都开上坡，然后卡在坡上。

Astra 拿到全部权重、场景描述和一局的录像，**一次回复、没有工具**，要求是：先解释失败的原因，然后只修这个原因。

结果：修改了 3.5% 的权重（6,073 个），**1,024 局全部成功**。

## 4.2 背景：局部最优

PPO 的策略陷在一个局部最优里：慢慢开上坡，得到一点"接近目标"的奖励，然后停在那里。
要想成功，必须先**远离**目标（倒车）来积累冲刺距离，而这在训练初期几乎从来不会被采样到，所以策略永远学不到。

**有趣的地方**：修复不需要重新训练。只要在网络里加一条"旁路"：从静止开始先倒车，到了某个位置之后全速向左，过了红色地带之后旁路自动关闭，剩下的路交还给原来的网络。

## 4.4 让 Claude 做

```bash
tutorial/tools/ask_claude.sh upstream/exp4_fix_car/runs/oneshot_repair/reply/prompt.txt mycar1 high
tutorial/tools/e4_score.sh tutorial/my_runs/mycar1/answer.md 1024
```

prompt 有 58 万字符，按 Claude 的分词是 **43.6 万 token**（Astra 那边是 35.5 万）。Claude Code 里的 `opus` 默认就是 1M 上下文，不用改任何参数。
一次运行大约 2 到 3 分钟，按 API 价格约 $3.8；同一小时内再发同样的 prompt 会命中缓存，只要约 $0.35。

Claude 三次的诊断都和 Astra 一致：网络从来不选"倒车"（值 2 的概率始终是 0.00），从静止直接爬坡，到坡顶时速度不够，
车身卡在坡顶的棱角上，绿轮悬在红条上方，之后在"关 / 前进"之间来回抖动，一直到超时。
修法也是同一个思路：先向右倒车到 x ≈ 3.5 到 3.7，再全力向左冲坡、飞过红条。

实现方式比 Astra 更简单：只读两个观测量（52 号是车身 x，54 号是车身 vx），每层只用 1 到 3 个单元串成一条链，
在输出头把动作 0 的三个 logit 完全接管（"关"压到 −20，左 / 右是 ±8 到 ±10）。所以新策略几乎是确定性的，每局的步数都一样。

### 思考题

1. Claude 的 r1 用 `ZERO actor1.W` 这类语句把 5 个隐藏层整层清零，改了 50% 的权重，但照样全部成功。
   它违背了 prompt 里"保留已经能用的部分"的要求吗？在这一关里，原网络还有哪部分"能用"？（提示：6 个动作分量里只有一个真的驱动了东西。）
2. 新策略几乎是确定性的，所以 1,024 局全部成功几乎是必然的。把回答里输出头的左 / 右 logit 幅度缩小（比如 ±8 改成 ±1，这时选对方向的概率只有约 88%），成功率会怎么变？复制一份 answer.md 改一下，再用 `e4_score.sh` 试一试。

## 4.5 对照

| | 结果（1,024 局） | 改动 | 语句 |
|---|---|---|---|
| Astra（1 次） | 1,024 / 1,024 | 3.54%（6,073 个） | 51 |
| **Claude Opus 5.5（3 次）** | **1,024 / 1,024，3 次都是** | 1.48% / **50.3%** / 1.70% | 33 / 32 / 30 |

结论：复现成功，而且 3 次都成功。改动比例的差别主要取决于"清零的时候是只清用到的几个单元，还是整层全清"，和能不能修好无关。
